## 1. 当前路线与使用方式

用户已认可当前 HTML 战斗玩法，并批准把后续阶段写入整体流程。D2-01 的体验目标与范围已完成，见[开场 Demo 设计](opening-demo-design.md)；用户于 2026-10-16 确认 [《憨之轨迹》· 序章·归来](<《憨之轨迹》· 序章·归来.md>) 为前期剧情初稿。D2-02 接下来整理可玩事件、游戏内必要对白与分段教学，先确定第二战的接入位置；D2-03～D2-05 待开始，D3 整体 Demo 与 Unity 工程均未实施。

当前路线为：**已完成的战斗参考 → 开场内容设计与美术基线 → HTML 整体最小 Demo → Unity 技术与美术样片 → Unity 开场可玩切片 → 内容扩展与打磨 → 毕业展示交付。**

这一安排替代了之前“下一步直接准备 Unity 战斗移植”的建议。D0、D1 编号保留；D2 起采用本文的新含义。人工手感、输入窗口、镜头与数值调节贯穿后续开发，不再作为独立编号阶段。旧 P0～P5 六边形卡牌路线保留在文末用于追溯，旧 P1-01 不是当前任务。

使用约定：

- 本文维护阶段、任务编号、依赖和验收；[开发交接](development-handoff.md)维护接续入口与当前待定项；[《憨之轨迹》· 序章·归来](<《憨之轨迹》· 序章·归来.md>) 保存当前认可的开场剧情；[基础稿 v0.2](opening-story-draft.md)与[早期设定](game-setting.md)用于历史对照；[开场 Demo 设计](opening-demo-design.md)保存范围选择；[1V1 交接](hanser-duel-handoff.md)与新版原型说明保存战斗依据。
- 状态使用“待开始 / 进行中 / 待验证 / 已完成 / 阻塞”。写完计划不等于完成阶段，测试通过也不能代替用户对整体体验的认可。
- 按下表依赖推进。阶段出口有未解决的关键问题时，先回到对应任务调整，不以新增内容掩盖问题。
- 每次写入前列出具体文件、修改、影响与验证方式，按用户规则取得批准；已批准范围内连续完成，范围变化重新确认。路线获批不等于未来文件、资源生成、安装、提交或推送获批。
- 不预设毕业日期、周数或正式关卡数量。D2 确定最小范围，D5 后结合可用时间与毕业要求决定 D6 的内容量。
- 每阶段同步留存设计取舍、真实测试结果与可复现步骤；截图、录屏等需要落盘时纳入该次写入范围，为论文和答辩积累真实材料。

- 鼠标和键盘分别完成胜利，战败重试、换装、大招、暂停与部分窗口尺寸检查；历史自动回归为 39/39 通过。

证据与入口：[可玩 HTML](../prototypes/hanser-duel/index.html)、[操作和临时数值](../prototypes/hanser-duel/README.md)、[实际验证记录](../prototypes/hanser-duel/VERIFICATION.md)。

## 4. D2：开场内容设计与美术基线

**目标：决定最小 Demo 要让玩家经历什么，并把剧情、操作、空间和资源需求一起确定。** 本阶段以设计和清单为主，不开展整套正式美术生产。

当前故事依据：[《憨之轨迹》· 序章·归来](<《憨之轨迹》· 序章·归来.md>)，前期初稿已获用户确认。流程为返乡家门前听到毛怪俱乐部疏散广播 → 满穗被追击、魔导盘掉落 → 拾取后外观变化并首战 → 将昏迷的满穗带回家，待她醒来讲述情况与礼物前史 → 满穗提出前往憨塔联系真正的憨 → 小镇调查、害怕与小册子引出的当下自省 → 决定前往憨塔。憨努努已移除，不恢复主角生气或后悔遇到追逐的描写。小说只展开首战，D2-01 的法师型第二战仍保留，其接入位置待设计。

D2-01 已获用户确认并写入[开场 Demo 设计](opening-demo-design.md)：外围道路和镇内小街区两处小区域、两场 1V1、两个可任选调查顺序的必需调查点，以及一个可删的环境调查点。演示从返乡开始，到玩家开始前往憨塔为止，不进入塔内。确认稿以家门前为叙述起点，家门与屋内对白如何对应两区域和可玩入口，需在事件与地图设计中落实，尚未批准增加探索区域。**首轮约 10～15 分钟是已确认的设计目标，排除失败重试和长时间研究装配，尚未实测；敌人具体技能、美术、教学细节与跨战斗规则仍待后续设计。**

| 任务 | 状态 | 工作与交付 | 验收条件 |
| --- | --- | --- | --- |
| D2-01 体验目标与范围 | 已完成；2026-10-15 用户批准 | [范围说明](opening-demo-design.md)：玩家情绪与操作目标、起点／终点、必做／可删／不做项、试玩目标时长及假设 | 用户已确认体验目标和关键边界；完成设计验收，未宣称整体试玩通过 |

设计限制：

- 广播由毛怪俱乐部向居民发出，内容为尽快离开小镇；不恢复“神主已经变了”的神使广播。首战后满穗昏迷，由毛怪带回家中，醒来后在床上说明情况。
- 满穗提供初始能力与陪伴，发现毛怪能使用魔导盘后，请他带自己前往憨塔联系真正的憨；毛怪调查后自行决定。憨努努已移除，小册子唤起的是当下对陪伴的感受，不新增具体回忆过场；寄宿机制与部分信物衔接仍待讨论。
- 战士型与法师型是已确认的敌人定位；新技能、外形、台词与教学用途要分别标记为提案或已确认内容。
- 先评估二维角色在三维场景中的朝向、阴影和遮挡需要；最终资产路线在 D4 用真实引擎样片验证。
- AI 辅助美术先有尺寸、朝向、风格和动作需求，再制作少量样例。素材参考与来源随清单记录；本阶段计划不自动授权生成、下载或购买资源。

**阶段出口：** D2-01～D2-05 的范围和关键选择已确认，形成可执行的 D3 清单；标出占位内容与尚未确定的正式内容。结束后下一项为 D3-01。

验证重点：

- 分别使用鼠标、键盘完成整个流程，检查切换输入、菜单取消、对话推进和任务提示。

## 6. D4：Unity 技术与美术样片

**目标：用尽量小的真实引擎样片，验证 2.5D 空间、角色与摄像机配合及资源制作成本。** 这阶段同时验证技术与美术，不只用占位方块证明程序能运行。

| 任务 | 状态 | 工作与交付 | 验收条件 |
| --- | --- | --- | --- |
| D4-01 环境与工程方案 | 待开始 | 只读检查现有 Unity、系统与工具；明确版本、Windows 目标、渲染方案、工程位置、依赖和文件范围 | 环境与工程方案明确，所需创建／安装范围获批 |
| D4-02 场景与角色样例 | 待开始 | 一处开场场景样例、一只毛怪、一个敌人占位或样例；透视、朝向、阴影、遮挡 | 角色转向与相机变化自然，不明显穿帮；图形风格能代表预期方向 |
| D4-03 镜头、动作与输入同步 | 待开始 | 指令、目标、攻击、受击与大招构图样例；代表性逐击时序与键鼠输入 | 读招与提示不被镜头遮挡；判定与动作同步，暂停恢复不额外结算 |

不在没有样片证据时宣称 HTML 的 2.5D 表现已验证 Unity 管线；不一次采购或生成整套正式资产。选择适用的角色方式后再扩量，必要时缩减镜头转角或动作需求以保证可实现性。

## 7. D5：Unity 开场可玩切片

**目标：把 D3 已认可的完整开场与 D4 的表现方法结合，做成可独立运行的最小游戏。**

| 任务 | 状态 | 工作与交付 | 验收条件 |
| --- | --- | --- | --- |
| D5-01 战斗核心与输入迁移 | 待开始 | 将已确认的 1V1 规则迁到 C#，动作和表现使用统一的战斗时序；两种输入共用规则 | 与 HTML 的关键场景结果一致，逐击反应、资源、大招插入等有对应验证 |
| D5-02 探索、对话与流程接入 | 待开始 | 开场地图、事件、对话、两场战斗、任务提示、结果与恢复流程 | D3 的完整路线在 Unity 内走通；跨场状态、取消与重试正确 |
| D5-03 代表性资源与反馈 | 待开始 | 按 D4 方法替换关键场景／角色，补齐必要动作、镜头、UI、特效、基础音效和教学 | 关键视觉不再依赖无法辨认的占位；角色、反馈与故事节奏协调，素材量保持最小 |

## 4. P1 战斗反馈与操作体验

### P1-01 行动过程与结果反馈【下一项】

**状态：待开始。依赖：P0。**

内容：

- 移动增加短过渡，攻击增加命中闪烁或伤害数字，回血显示回复数字；空挥也应看得出动作已执行。
- 先设计最小的行动结果记录，包含必要的单位标识、起终点、伤害或回复、死亡等信息，供界面顺序展示。
- 将表现时长等临时参数集中配置；保持几何占位，不引入正式资源和复杂动画框架。

实现注意：当前 Game 同步结算并立即重绘最终状态，不能只在最终画面上增加延时。建议保留规则结算产生的结果，用独立展示状态播放；动画不重复调用伤害、移动、随机抽牌或回合结算。具体拆分方式在实施检查后列明。

预计涉及：原型 index.html、必要的规则 / 行动结果测试、原型说明和验证记录。新增文件在实施方案中列出。

验收：

- 一次移动、攻击、回血只执行一次，展示结果与规则状态一致。
- 击退、击杀、空挥均能结束展示，无目标不会卡住动画。
- 同种子、同操作在不同表现速度下，最终生命、位置、卡牌、冷却和回合一致。
- 连续点击、拖牌与快捷键不能在播放期间重复提交；本项先提供最小输入锁，P1-02 完善敌方播放。
- 原有规则测试通过；实际验证移动、伤害、回血和空挥。

### P1-02 敌人逐个行动与播放期间的输入限制

**状态：待开始。依赖：P1-01。**

内容：按已有顺序展示敌人移动、攻击、等待和备招，突出当前行动单位；展示结束后才恢复玩家可操作状态。

预计涉及：行动结果展示、所有输入入口、阶段提示及相关测试。

验收：

- 敌人逐个展示，提前被击败的单位不播放尚未发生的攻击。
- 预告移动被占用时展示失败，不临时改为攻击。
- 连招逐招等待玩家选方向；整组结束后才展示敌方行动。
- 鼠标、点击、键盘都遵守输入锁；切换窗口或取消拖动不重复结算，也不永久锁死。
- 伤害、死亡、超限弃牌、冷却、新回合与结果浮层按原型既定顺序展示，不提前开放下一回合操作。

### P1-03 拖牌预览与具体失败提示

**状态：待开始。依赖：P1-02。**

内容：在已有合法格高亮与连招范围预览上完善目标辨识；失败时区分距离不足、障碍、占用、需要敌人和阶段限制。窄窗口保留底部卡牌滚动。

预计涉及：目标解析、校验结果、战场预览与提示文本。

验收：

- 高亮和实际允许的目标一致，不维护互相矛盾的两套判断。
- 无效拖放、Esc、松手在空白区不消耗卡牌、回合或冷却。
- 普攻不能空挥；组合招式可空挥且必须执行到底。
- 移动、闪现、回血、序列加入 / 排序 / 移出和弃牌均验证合法与错误目标。
- 1280×900、1366×768、630×892 下操作区可见，没有拖放遮挡或误触。

### P1-04 连招、抽弃牌与冷却提示

**状态：待开始。依赖：P1-03。**

内容：突出当前招式和第几招 / 总招数；展示抽牌、用牌、弃牌变化；冷却减少或恢复可选时给予短提示；超限时显示还需弃几张。

## 10. 每次交付检查

3. 记录配置、种子、实际结果与未验证项。
4. 更新任务状态、验证记录和交接的下一项，不把待验证写成已完成。
